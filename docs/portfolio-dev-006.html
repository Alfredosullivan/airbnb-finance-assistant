Overview

Problema

El railway.json tenía 4 líneas con builder implícito y sin healthcheck. Railway marcaba el deploy como exitoso en el momento en que el proceso de Node.js arrancaba, sin esperar a que la DB estuviera disponible. El endpoint /health respondía 200 incluso si PostgreSQL estaba caído.

Solución

Se declaró el builder explícito como DOCKERFILE y se configuró healthcheckPath, healthcheckTimeout y restartPolicyMaxRetries. El endpoint /health ahora ejecuta SELECT 1 contra el pool de PostgreSQL y responde 200 (ok) o 503 (degraded) según el resultado.

Contexto del proyecto

Airbnb Finance Assistant es una aplicación Node.js + Express + PostgreSQL desplegada en Railway. El proyecto cuenta con CI/CD (GitHub Actions, 4 jobs), Docker multi-stage, secret scanning con Gitleaks y CVE scanning con Trivy. DEV-006 forma parte de la fase de madurez de infraestructura, aplicando los principios de IaC que ya existían en docker-compose.yml al archivo de configuración de Railway.

Decisiones técnicas

🏗️

builder: "DOCKERFILE" explícito

Railway puede auto-detectar el Dockerfile en la raíz, pero el buildCommand anterior creaba ambigüedad: Railway podía usar Nixpacks e ignorar el Dockerfile multi-stage. Declarar el builder elimina la ambigüedad y garantiza que se use la imagen optimizada.

✓ Elegido: IaC debe ser explícito. La configuración implícita es deuda técnica disfrazada de conveniencia.

✗ Descartado: dejar que Railway auto-detecte. Funciona hoy, falla silenciosamente si Railway cambia la heurística.

🩺

SELECT 1 como query de healthcheck

SELECT 1 es la consulta más barata posible: no lee ninguna tabla, no genera I/O de disco, no requiere permisos especiales. Si el motor de PostgreSQL la procesa, la conexión está viva y el pool funciona.

✓ Elegido: mínimo overhead, máxima frecuencia segura. El healthcheck se llama en cada deploy y potencialmente cada N segundos.

✗ Descartado: consultar una tabla real. Agregaría I/O innecesario y dependería del schema.

🔢

HTTP 503 cuando la DB está caída

503 Service Unavailable indica que el servicio existe pero no puede atender requests en este momento. Es el código correcto cuando una dependencia externa (la DB) no está disponible.

✓ Elegido: semántica HTTP correcta. Permite que load balancers y orquestadores tomen decisiones de routing inteligentes.

✗ Descartado: 500 Internal Server Error. Implica un bug del servidor, no una dependencia caída. Confunde monitoreo y alertas.

⏱️

healthcheckTimeout: 100 segundos

Railway espera hasta 100 segundos a que /health responda 200 antes de marcar el deploy como fallido. Una app Node.js con PostgreSQL tarda tipicamente 5-15 segundos en arrancar; 100s da margen para starts lentos sin ser demasiado permisivo.

✓ Elegido: balance entre velocidad de detección de fallos y tolerancia a starts lentos en producción.

✗ Descartado: 300s (default). Demasiado tiempo sin detectar un deploy roto.

Flujo del deploy con healthcheck

git push origin main → dispara el pipeline en Railway
↓ Railway lee railway.json
builder: "DOCKERFILE" → usa el Dockerfile multi-stage de la raíz
dockerfilePath: "Dockerfile" → ruta explícita, sin ambigüedad
↓ imagen construida → contenedor iniciado
↓ Railway llama GET /health cada 5s (hasta 100s)
handler async → pool.query('SELECT 1')
✓ responde → 200 { status: 'ok', services: { database: 'ok' } }
↓ deploy marcado SUCCESS ✓

✗ lanza excepción → 503 { status: 'degraded', services: { database: 'error' } }
↓ restart (ON_FAILURE, máx 10 intentos)
↓ si >10 reinicios → deploy marcado CRASHED

railway.json final

// railway.json — Infraestructura declarativa para Railway
{
  "build": {
    "builder": "DOCKERFILE",            // builder explícito — sin ambigüedad Nixpacks
    "dockerfilePath": "Dockerfile"   // ruta al multi-stage build
  },
  "deploy": {
    "startCommand": "node dist/index.js",
    "healthcheckPath": "/health",     // Railway confirma app lista
    "healthcheckTimeout": 100,      // segundos máximos para arrancar
    "restartPolicyType": "ON_FAILURE",
    "restartPolicyMaxRetries": 10  // máx reinicios antes de CRASHED
  }
}

endpoint /health

// GET /health — Liveness + readiness probe
app.get('/health', async (_req, res) => {
  const health = {
    status: 'ok',
    uptime: process.uptime(),
    timestamp: new Date().toISOString(),
    services: { database: 'ok' },
  };

  try {
    await pool.query('SELECT 1');  // ping más barato posible a PostgreSQL
  } catch (err) {
    logger.error('[health] DB check fallido:', { err: err.message });
    health.status = 'degraded';
    health.services.database = 'error';
  }

  res.status(health.status === 'ok' ? 200 : 503).json(health);
});

Features implementadas

Builder declarativo IaC

builder: "DOCKERFILE" garantiza que Railway usa el Dockerfile multi-stage optimizado, no Nixpacks. Elimina la ambigüedad que existía con el buildCommand anterior.

Healthcheck configurado IaC

Railway ahora llama GET /health antes de marcar el deploy como exitoso. Sin esto, el deploy se consideraba exitoso cuando el proceso arrancaba, no cuando la app estaba lista.

Readiness probe real API

El endpoint verifica PostgreSQL con SELECT 1 vía el pool de conexiones. Si la DB no responde, la app se considera no lista para atender tráfico.

Respuesta estructurada API

El body incluye status, uptime, timestamp y services.database. Parseable por cualquier sistema de monitoreo.

HTTP 200 / 503 semántico API

200 cuando todo está ok. 503 cuando la DB está caída pero la app sigue viva. Permite que load balancers y orquestadores tomen decisiones de routing correctas.

Restart policy con límite Ops

restartPolicyMaxRetries: 10 evita reinicios infinitos. Si hay un bug de arranque, Railway marca CRASHED después de 10 intentos y notifica al developer.

Problemas reales encontrados y resueltos

BUG-01 Builder ambiguo: Nixpacks vs Dockerfile

Causa técnica

El railway.json tenía buildCommand: "npm install && npm run build" que es sintaxis de Nixpacks, pero el proyecto también tenía un Dockerfile en la raíz. Railway podía usar cualquiera de los dos según su heurística interna, ignorando el Dockerfile multi-stage optimizado con sus capas de seguridad (apk upgrade, npm@11.19.1).

Fix aplicado

Reemplazar buildCommand por builder: "DOCKERFILE" + dockerfilePath: "Dockerfile". Declarativo y sin ambigüedad.

BUG-02 Healthcheck fantasma: Railway no sabía que /health existía

Causa técnica

El endpoint /health estaba implementado en index.js pero nunca fue declarado en railway.json. Railway marcaba el deploy como exitoso en cuanto el proceso de Node.js arrancaba, sin verificar que la aplicación pudiera atender requests reales. Un deploy con la DB desconectada pasaría como exitoso.

Fix aplicado

Agregar healthcheckPath: "/health" y healthcheckTimeout: 100. Ahora Railway espera confirmación real antes de marcar el deploy.

BUG-03 Liveness sin readiness: DB caída = 200 igual

Causa técnica

El handler original de /health era síncrono y solo retornaba {"status": "ok"} sin verificar ninguna dependencia. Si PostgreSQL estaba caído, el endpoint seguía respondiendo 200. Railway pensaría que la app estaba lista cuando en realidad no podía procesar ningún request.

Fix aplicado

Handler convertido a async con await pool.query('SELECT 1') en un try/catch. Si falla: status: "degraded" + HTTP 503.

BUG-04 Reinicio infinito por ausencia de maxRetries

Causa técnica

restartPolicyType: "ON_FAILURE" sin restartPolicyMaxRetries significa que Railway podría reiniciar el contenedor indefinidamente si hay un bug de arranque, consumiendo recursos y ocultando la causa raíz del fallo bajo una cascada de logs de restart.

Fix aplicado

Agregar restartPolicyMaxRetries: 10. Después de 10 intentos fallidos, Railway marca el servicio como CRASHED y notifica, permitiendo diagnóstico sin ciclos infinitos.

BUG-05 Rama fantasma: git push recreó una rama ya eliminada

Causa técnica

El usuario ya había mergeado el PR y eliminado la rama refactor/sdd-migration en GitHub. El commit del healthcheck se hizo localmente después del merge y se intentó subir con git push origin refactor/sdd-migration, recreando la rama eliminada en el remoto.

Fix aplicado

Eliminar la rama remota recién creada con git push origin --delete refactor/sdd-migration, hacer checkout de main, pull, cherry-pick del commit sobre main, push a main, y borrar la rama local con git branch -D.

Preparación para entrevista

Q1 ¿Tienes experiencia con IaC? ¿Qué herramientas conoces?
Sí. En este proyecto usé tres capas de IaC: docker-compose.yml para orquestar servicios locales (app + PostgreSQL, redes, volúmenes, healthchecks), railway.json para declarar el build y deploy en Railway, y .github/workflows/ci.yml como pipeline-as-code con 4 jobs. Conozco Terraform, pero no lo apliqué porque el tamaño del proyecto no lo justificaba — Terraform agrega valor cuando tienes multi-cloud o múltiples entornos con infraestructura compleja. Saber cuándo no usar una herramienta es tan importante como saber usarla.
Q2 ¿Cuál es la diferencia entre liveness probe y readiness probe?
Un liveness probe responde "¿el proceso está vivo?". Un readiness probe responde "¿puede atender tráfico?". Son preguntas distintas: un proceso puede estar vivo pero no listo (conectándose a la DB, calentando caché). En Kubernetes se mapean a dos endpoints separados: /healthz para liveness y /readyz para readiness. En Railway se unifica en healthcheckPath, por lo que implementé ambas verificaciones en un solo endpoint: proceso vivo + DB disponible.
Q3 ¿Por qué 503 y no 500 cuando la DB está caída?
503 Service Unavailable significa "el servicio existe pero no puede atender requests en este momento", típicamente por una dependencia externa caída. 500 Internal Server Error implica un bug del servidor. Cuando la DB está caída no es un bug de la app — es una dependencia no disponible. El código correcto importa para monitoreo: las alertas de un equipo pueden tener thresholds distintos para 500s y 503s. Además, los load balancers pueden usar el código HTTP para tomar decisiones de routing.
Q4 ¿Qué hace SELECT 1 y por qué es la consulta ideal para un healthcheck?
SELECT 1 hace que el motor de PostgreSQL procese una expresión constante sin leer ninguna tabla, sin I/O de disco y sin requerir permisos más allá de una conexión válida. Si responde, sabemos tres cosas: el pool de conexiones está operativo, el servidor PostgreSQL está procesando queries, y la red entre app y DB funciona. Es el mínimo check significativo con el menor costo posible.
Q5 ¿Qué es un cherry-pick y cuándo lo usarías?
git cherry-pick <hash> toma un commit específico de cualquier rama y lo aplica sobre la rama actual como un commit nuevo (con hash diferente). Lo usé cuando el commit del healthcheck quedó fuera del merge: en vez de rehacer el trabajo manualmente o crear una nueva rama, cherry-pick trasladó exactamente ese cambio a main. Es útil para backports (llevar un fix de main a una rama de release) o para situaciones como esta donde un commit quedó huérfano por un merge mal coordinado.
Q6 ¿Por qué declarar el builder explícitamente si Railway puede auto-detectarlo?
Porque la configuración implícita es deuda técnica disfrazada de conveniencia. Si Railway cambia su heurística de auto-detección en una actualización, el build podría cambiar de Dockerfile a Nixpacks silenciosamente, sin ningún error visible, pero con una imagen diferente en producción. IaC debe ser explícito y reproducible: el mismo railway.json debe producir el mismo resultado hoy y en seis meses.
Q7 ¿Qué problema resuelve restartPolicyMaxRetries?
Sin un límite de reinicios, un bug de arranque (por ejemplo, una variable de entorno faltante) haría que Railway reiniciara el contenedor infinitamente, consumiendo recursos y generando cientos de líneas de logs idénticos que ocultan la causa raíz. Con restartPolicyMaxRetries: 10, después de 10 fallos Railway marca el servicio como CRASHED y detiene los reinicios. Eso fuerza al developer a investigar el log del primer intento fallido, que contiene el error real.
Q8 ¿Cuándo usarías Terraform o Pulumi en vez de este enfoque?
Cuando la infraestructura sea compleja y necesite reproducirse consistentemente en múltiples entornos: dev, staging, prod con recursos separados en la nube. Por ejemplo, si tuvieras múltiples microservicios, una VPC, subnets, security groups, un CDN, y una base de datos managed — Terraform permite describir todo eso como código con state management y plan/apply. Para este proyecto (1 app + 1 DB en Railway), railway.json y docker-compose.yml son la solución proporcional. Sobreingeniería es un bug.
