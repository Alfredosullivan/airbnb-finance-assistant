🐛Problema Original

Descubrimiento crítico: El script fix-negative-comision.js creado en DEV-004 apuntaba a data/finance.db mediante better-sqlite3. Esa es la base de datos SQLite del stack legacy, no la base de datos de producción de la aplicación. La aplicación migró a PostgreSQL meses antes. El script era inoperante contra los datos reales.

Contexto del descubrimiento

Al intentar ejecutar el dry-run original, el proceso falló con error de native bindings: 

Error: Cannot find module '../build/Release/node_sqlite3.node'

La investigación reveló que:

  • data/finance.db existe en el repositorio pero es un artefacto del stack legacy, no la base de datos de producción.
  • src/database/db.js (SQLite) no es importado por ningún módulo de la aplicación — verificado con grep -r "require.*database/db" src/ → 0 coincidencias.
  • Toda la aplicación usa PostgreSQL vía src/database/client.js y DATABASE_URL.
  • better-sqlite3 requiere bindings nativos compilados por versión de Node.js y arquitectura — no disponibles para Node.js v20.20.2 en Windows x64.

⚙️Decisiones de Diseño

Decisión 1 — Usar pg directamente con Pool propio, no reutilizar src/database/client.js

Razón: client.js es un singleton diseñado para el servidor Express: no llama dotenv.config() (el servidor ya lo hizo) y nunca llama pool.end() (el proceso del servidor no termina). Un script de Node.js sí debe llamar pool.end() en finally para que el proceso pueda salir limpiamente. Reutilizar el singleton haría el proceso colgar indefinidamente.

Patrón de referencia: scripts/migrate.js establece el mismo patrón: require('dotenv').config() → validar DATABASE_URL → new Pool() propio → client.release() + pool.end() en finally.

Decisión 2 — Filtrar en JavaScript, no con SQL JSONB casting

Razón: La columna summary es TEXT NOT NULL, no JSONB. Usar summary::jsonb en SQL fallaría toda la query si cualquier fila tiene JSON inválido. El filtro en JavaScript con try/catch individual por fila aísla errores: un JSON inválido solo incrementa el contador totalErrores y continúa con los demás registros.

Decisión 3 — Transacción solo en modo real, no en dry-run

Razón: En dry-run el script nunca emite UPDATE, por lo que abrir una transacción sería innecesario y podría dejar conexiones idle en producción si el proceso se interrumpe. La flag dryRun controla qué bloques se ejecutan: BEGIN/COMMIT/ROLLBACK solo existen en el branch real.

Decisión 4 — rowCount === 1 como guardia post-UPDATE

Razón: Un UPDATE que devuelve rowCount !== 1 indica que el registro desapareció entre el SELECT y el UPDATE (lo cual no debería ocurrir, pero el script actúa sobre producción). Lanzar un error en ese caso activa el ROLLBACK automáticamente: ningún cambio parcial queda en la base de datos.

Decisión 5 — No usar FOR UPDATE en el SELECT

Razón: La operación es idempotente: Math.abs(comision) de un valor ya positivo da el mismo valor positivo. No hay riesgo de corrupción por ejecuciones concurrentes del script. FOR UPDATE añadiría bloqueos innecesarios y latencia en producción sin beneficio real.

🎓Engineering Takeaways

¿Qué lección de arquitectura demuestra DEV-005?
Un script que apunta a la base de datos equivocada es técnicamente inoperante sin importar qué tan correcto sea su código. El diagnóstico de "no funciona" nunca debe empezar por el código — debe empezar por verificar las dependencias del entorno: ¿qué base de datos usa la aplicación real? ¿coincide con lo que el script asume?
¿Por qué el script crea su propio Pool en lugar de importar el de la aplicación?
El singleton src/database/client.js está diseñado para procesos de larga duración (el servidor Express). No llama pool.end() porque el servidor no termina. Un script de Node.js necesita cerrar el pool explícitamente en finally para que el proceso pueda salir. Reutilizar el singleton dejaría el proceso colgado esperando conexiones abiertas.
¿Cuál es el protocolo de seguridad para ejecutar scripts de corrección en producción?
El protocolo de tres capas aplicado: (1) dry-run local con datos sintéticos controlados para validar la lógica del script; (2) dry-run en producción para conocer el alcance real antes de cualquier cambio; (3) migración real solo con aprobación explícita posterior a la revisión del reporte de dry-run. En este caso el dry-run de producción mostró 0 afectados, por lo que la migración real nunca se ejecutó — lo que es también un resultado correcto.
¿Por qué se filtra en JavaScript y no con SQL JSONB casting?
La columna summary es TEXT NOT NULL, no JSONB. Usar WHERE summary::jsonb->>'excelData' en SQL fallaría toda la query si alguna fila tiene JSON malformado. Filtrar en JavaScript con try/catch individual aísla el error a la fila afectada, permite contabilizarla como error, y continúa procesando el resto. Siempre hay que conocer el tipo real de la columna antes de hacer asunciones sobre operaciones SQL.
¿Cómo se usó Railway CLI para conectar a producción sin exponer credenciales?
railway run --service Postgres inyecta las variables de entorno del servicio directamente en el proceso hijo — incluyendo DATABASE_PUBLIC_URL — sin que el valor aparezca en ningún archivo local ni en el historial de Git. El script lee DATABASE_URL de su entorno de proceso, no de un archivo. Este es el patrón correcto para cualquier script que necesite conectarse a servicios de producción desde una máquina local.
