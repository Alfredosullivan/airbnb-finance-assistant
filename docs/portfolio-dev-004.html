🐛Problema Original

Bug: excelData.comisionAirbnb se guardaba con valor negativo en la base de datos cuando el CSV de Airbnb reportaba serviceFee como deducción contable (ej. −200). El campo debía ser siempre una magnitud positiva que representa el costo de comisión.

Causa Raíz

El CSV de Airbnb reporta serviceFee con signo negativo porque en su contabilidad interna es una deducción del pago al anfitrión. Ninguno de los tres sitios que calculaban comisionAirbnb aplicaba Math.abs() antes de persistir el valor. El valor se guardaba con el signo original del CSV.

Impacto

  • Los reportes Excel generados mostraban comisión negativa, confundiendo la interpretación financiera.
  • El análisis IA (Hoja 4) recibía datos incorrectos para el cálculo de métricas.
  • Los reportes guardados desde sesión activa (Fuente 1) eran los únicos afectados con datos persistidos incorrectamente.

Por qué parseMonto() no era el lugar del fix

El parser CSV es correcto por diseño: preserva el signo del dato fuente para fidelidad de los datos brutos. La transformación semántica (deducción contable → costo positivo de dominio) pertenece a la capa de lógica de negocio, no al parser.

⚙️Decisiones de Diseño

Decisión 1 — Crear helper canónico en utils/ en lugar de repetir Math.abs() en 3 sitios

Razón: Tres sitios independientes calculaban la misma transformación de forma duplicada. Un helper centralizado garantiza que cualquier futuro consumidor herede el comportamiento correcto sin necesidad de recordar aplicar Math.abs().

Alternativa descartada: Aplicar Math.abs() directamente en cada sitio. Viola DRY y deja la regla de dominio implícita en tres lugares distintos.

Decisión 2 — No modificar csvParser.js

Razón: El parser es correcto. La fidelidad del dato fuente es una responsabilidad diferente a la transformación de dominio. Separar estas capas es SOLID / Single Responsibility.

Decisión 3 — Firma del helper: calcularComisionDesdeReservaciones(entries)

Razón: Recibe el array de entries completo (no una reservación individual) para poder acumular noches y comisionAirbnb en un solo recorrido. Retorna ambos valores juntos porque siempre se necesitan en par. Inmutable: no muta los objetos de entrada.

Decisión 4 — Fallback en migrate-excel-data.js con guard mutually exclusive

Razón: Datos históricos (pre-DEV-003) tenían nights y serviceFee en nivel raíz, sin array reservations[]. El helper solo procesa entradas con reservations[] válido; el fallback cubre el caso histórico. El guard !Array.isArray(item.reservations) || item.reservations.length === 0 hace las dos ramas mutuamente excluyentes: no hay double-counting.

💻Implementación

Helper canónico — src/utils/airbnbMetrics.js (CREADO)

function calcularComisionDesdeReservaciones(entries) {
  if (!Array.isArray(entries) || entries.length === 0) {
    return { noches: 0, comisionAirbnb: 0 };
  }
  let noches = 0;
  let comisionAirbnb = 0;
  for (const entry of entries) {
    const reservations = Array.isArray(entry?.reservations) ? entry.reservations : [];
    for (const r of reservations) {
      noches += parseInt(r?.nights, 10) || 0;
      comisionAirbnb += Math.abs(parseFloat(r?.serviceFee) || 0);  // ← fix
    }
  }
  return { noches, comisionAirbnb };
}
module.exports = { calcularComisionDesdeReservaciones };

🎓Engineering Takeaways

¿Qué patrón de diseño demuestra DEV-004?
Extracción de regla de dominio a helper canónico. Cuando la misma transformación aparece en 3+ lugares, el fix correcto no es añadir Math.abs() en cada sitio sino crear una función con nombre significativo que exprese la intención del dominio (comisión = magnitud positiva del serviceFee). Esto aplica Open/Closed: nuevos consumidores del helper heredan el comportamiento sin modificación.
¿Por qué no se corrigió en el parser del CSV?
El parser tiene una responsabilidad: leer el dato fuente con fidelidad. Transformar la semántica del dato (deducción contable → costo de dominio positivo) es responsabilidad de la capa de negocio. Mezclarlas viola Single Responsibility y hace el parser menos reutilizable para otros consumidores que sí necesiten el signo original.
¿Qué técnica de testing se usó para cubrir el helper?
Testing unitario con cobertura de valores límite: null, undefined, string inválido, array vacío, null en raíz, e inmutabilidad. Más testing de integración end-to-end vía HTTP para verificar que el valor llega correctamente a la base de datos (no solo que el helper lo calcula bien en aislamiento).
¿Por qué se cambió .not.toBe(500) a .toBe(75) en el test de prioridad?
Una assertion negativa nunca prueba que el valor correcto está presente, solo que el valor incorrecto no está. expect(x).not.toBe(500) pasa con x = -75, x = 0 o x = null — todos valores incorrectos. expect(x).toBe(75) solo pasa con el resultado exacto esperado. DEV-004 requería verificar tanto que el signo era positivo como que la magnitud era correcta; la assertion negativa de DEV-003 no era suficiente para eso. La regla general: en tests de corrección de bugs, preferir assertions exactas sobre el valor esperado.
¿Cómo se garantizó que el fallback en migrate-excel-data.js no hace double-counting?
El guard !Array.isArray(item.reservations) || item.reservations.length === 0 es mutuamente excluyente con la condición del helper (que solo procesa entries con Array.isArray(entry.reservations) verdadero y longitud mayor a 0). Un entry procesado por el helper nunca entra al fallback, y viceversa. Es el mismo patrón de guard clause que se usa en validaciones: cada rama tiene su condición clara y exhaustiva.
